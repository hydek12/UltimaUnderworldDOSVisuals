# Repository instructions

- Put every change to `main` through a GitHub pull request. Work on a topic branch, push that branch, and open a PR against `main`. This applies to code, docs, fixes, and rollbacks.
- Use the PR template. Describe what changed and why, list measurable acceptance criteria, and record the checks actually run and their results. List any pending checks and distinguish emulator staging, normal controller input, build verification, and deployment where relevant.
- Update the affected project documentation in the same PR. Use a merge commit to preserve the PR as a discrete change that can be audited or reverted. Retain the GitHub PR and its verification evidence.
- Review and merge when authorized and the acceptance criteria are met. Follow GitHub's reviewer and merge permissions.
- Follow [the pull request workflow](docs/pull-request-workflow.md). For work that predates it, use [the historical commit log](docs/change-history.md).
- Follow the [project rules](docs/project-rules.md) for baselines, source-only releases, emulator verification, milestone criteria, and Slack reporting.

## Testing directions

- Preserve the original save and test from a disposable checkpoint or backed-up test memory card. Supply native recovery items as needed in the test copy, including before a run if the checkpoint lacks enough. Verify that any restocked save reloads. Verify the equipped gear, consumables, and original quest items before continuing.
- Use in-game inventory containers, such as sacks, when available and compatible with the test. Use normal controller inputs to store and retrieve items. Before a quest handoff, verify the original quest item is accessible in the inventory slot the interaction uses.
- Use normal controller input for acceptance runs. Equip appropriate armor, use recovery items through normal controller input as needed, and bypass enemies when the route allows. Before confirming or releasing an attack, aim the targeting reticle directly at the enemy if one is displayed. For attacks without a reticle, including charged sword strikes, center the enemy on screen before striking. Try a native damage spell when melee is ineffective.
- Use an in-game lighting item, such as a torch, when available and compatible with the test. Keep the required lighting conditions for darkness and comparison checks, and record which light source was active.
- Consult the in-game automap before attempting ledges, jumps, or unfamiliar turns. Plan routes through the center of known traversable corridors and platforms. Keep clearance from walls, ledges, and hazards, and approach an edge only for a deliberate crossing. Save at a safe approach. Verify questionable crossings in gameplay.
- Verify damage with enemy health before and after the action. A swing, a targeting reticle, or a visible projectile confirms input or casting. A health decrease attributable to the player confirms damage.
- When nearby enemies can converge, clear them one at a time where practical before proceeding. For suspected crowd-related slowdown, compare runs with enemies active and defeated from comparable checkpoints. Record enemy count, player vitality, game FPS, video FPS, and emulator speed.
- For a controlled defeated-enemy test, keep an untouched control and use a disposable memory-card copy. Fully exit DuckStation before copying, swapping, or editing a card file. Cold-boot and load the staged slot through the game, verify enemy and quest state, and resume with normal controller input. Record staged defeats as test setup.
- Use the [DuckStation combat diagnostic](lanugo/duckstation_combat.py) on an isolated, disposable QA session when a controlled defeat helps test a route or compare performance. Scan nearby creatures and review their disposition, vitality, and distance before explicitly selecting an actor. Record the command and measured result as test setup.
- When creating or changing combat tools, default to a read-only scan and verify the loaded executable before allowing writes. Limit damage to explicitly selected hostile actors whose native attack goal targets the player. Recheck identity, range, and disposition immediately before calling the native damage routine. Use current vitality as the damage amount and read back the result. Block friendly, neutral, and unconfirmed actors. Verify both an allowed defeat and blocked cases.
- Keep staging and verification distinct. Record any staged equipment, supplies, or position. Use read-only inspection during the run to confirm state. For route and quest checks, record each required transition and verify that the original item persists until the expected handoff or consumption.
- Save verified checkpoints separately, confirm the DuckStation exit dialog, and post verified results and pending checks in the GitHub PR and the `#projects` Slack thread.
